# git-r22 升级说明 · 两小时长文自动分段、合并与安全保底

## 本次解决的现场错误

截图显示 `AI_DOCUMENT_TOO_LARGE：章节多轮续写仍无终点`。经查 r21 在 `extension/longform-background.js` 使用通用 `build()`：一旦模型返回 `finish_reason=length`，就带上前段尾部继续生成；重复到 32 次后，无论原始输入是否已经充分覆盖，都直接失败。知识取材提示曾要求 **1300 字以内**，但对应输出上限仅 **750 tokens**，容易持续截断。这不是单纯的“章节太多”，因而再次缩短用户选择范围不是正确的长期策略。

## r22 策略

1. **正常情况**：沿用原有来源→取材→主题索引→章稿→跨章节主题合并，每个已完整返回的结果立刻保存，正常分块不额外拆小，减少模型调用数量。
2. **模型报告长度截断**：不再续写同一段最多32次，也不把截断输出冒充完整结果。按**原始来源**在语句/换行附近二分，分别重做短输入，再将完成的结果拼合，继续参加下一层主题去重。切分保持原字符次序、不修改来源 ID、不会丢掉原文。
3. **输入体积过大 / HTTP 413**：同样按来源拆小；401、403、429、500/5xx、超时等仍如实报错，不无意义重试、跳过鉴权或更换服务商。
4. **最小块仍连续截断**：递归有深度及最小容量上限，局部使用原始资料原样保底，并在最终“整理详情”记录受影响的内部阶段数量。这保障材料不丢失，但**不能宣称该片段已完成深度整合或语义核验**。
5. **断点续跑**：每个拆分节点及其完成状态有独立 Chrome 本地检查点。已经完成的 r21 取材/章节/主题结果沿用；旧的 `attempt=32` 未完成草稿另行保留为 `:r21-incomplete`，改从原始来源生成，不必从头删除整个视频。只在同一视频/模式/模型/来源范围时复用。
6. **修订生成目标**：证据提取不超过400汉字，全局索引不超过270汉字，章节400—650汉字，主题合并650—950汉字，以减少与每请求 `max_tokens` 上限冲突。

## Windows 原位升级

1. 停止整理、备份整个 `D:\VideoKnowledge_Git_Project`（包括个人配置、数据）。
2. 解压 r22 完整 ZIP，按相同结构**合并覆盖**原项目源码；不要删除 `.venv`、`.venv-qwen`、`models/`、`ASR_SETTINGS.bat`、SQLite、音频缓存、个人笔记。
3. 本次只修改 Edge 扩展整理算法及开发文档，无新 Python/Ollama/Sherpa 依赖。通常不需要重新安装 ASR 模型或重建虚拟环境。
4. 进入 `edge://extensions/`，找到**原来已经加载**的 VideoKnowledge，点击“重新加载”；刷新视频页面。不要卸载后重新安装，避免扩展 ID/存储发生变化。
5. 返回之前失败的两小时视频，在相同摘要模型、相同范围、相同整理模式再次点击“生成”，自动使用已保存的符合条件的检查点并处理新阶段。
6. 结果生成后查看“整理详情”的来源覆盖情况及“使用原始来源片段保底”标记。如果标记很多，说明当前模型持续截断，文档虽然可能生成，但需要降低期望的主题整合质量或换用能完整遵循指令的本地文字模型（必须由用户主动切换）。

## 兼容、回退与安全

- 原始听写、字幕、声音分组、现有知识文档不由本次迁移删除。新检查点只存于原有扩展的 Chrome storage；不要在升级时清除扩展数据。
- 回退到 r21：先备份当前目录和扩展数据，恢复 r21 源码并重载同一扩展。r21 无法识别新型自适应拆分子检查点，可能重新尝试其旧的最多32次续写；旧版 `:r21-incomplete` 草稿仍保留。
- 原生 Windows、真实两小时 Ollama/Edge 端到端质量、处理耗时与卡顿尚未完成现场验收。构造测试只验证代码可靠性，不证明摘要没有遗漏或模型一定能归纳同一主题。
